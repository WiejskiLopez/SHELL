# Pierwsza krytyczna zmiana: fail-fast konfiguracji produkcyjnej per usługa

## Status realizacji

Pierwszy krok został wdrożony:

- wspólny loader przyjmuje identyfikator usługi;
- siedem entrypointów przekazuje własny identyfikator;
- profil `prod` wymaga własnych zmiennych bazy, brokera i klucza API;
- dodano testy braku każdej z wymaganych wartości oraz test izolacji od `SHELL_*`;
- profil `dev` zachowuje dotychczasowe fallbacki.

Pozostałe punkty tego dokumentu są planem kolejnych etapów.

## Wniosek z `separacja.md`

`separacja.md` trafnie wskazuje, że niezależne wdrożenie wymaga własnej bazy, brokera, sekretów i cyklu release. Część jego diagnozy jest jednak nieaktualna:

- per-service event registry już istnieje dla wszystkich siedmiu usług;
- każda usługa ma własny kontener, entrypoint, Dockerfile, compose, migracje i lockfile;
- test kontraktu niezależnej usługi oraz testy izolacji przechodzą;
- obecna topologia używa `shell/<service>_service/`, a nie starego `shell/<bc>/`;
- nie ma już centralnego rejestru zdarzeń opisanego w dokumencie jako bieżący blocker.

Najważniejszy pozostały problem operacyjny to brak twardej granicy konfiguracji produkcyjnej. `LoadedConfiguration` dostarcza domyślny adres SQLite (`sqlite+aiosqlite:///shell.db`), pusty klucz API i pusty adres brokera. Entry pointy mogą też przejść na wspólny adres z konfiguracji platformowej, gdy brakuje zmiennej per usługa. Taki proces może wystartować w pozornie poprawnym trybie, ale użyć niewłaściwej bazy albo działać bez uwierzytelnienia.

## Proponowana zmiana

Dodać walidację fail-fast dla profilu `prod`, ograniczoną do granicy konfiguracji i composition rootów:

1. Każda usługa wymaga własnych zmiennych:
   - `<SERVICE>_SERVICE_DATABASE_URL`;
   - `<SERVICE>_SERVICE_BROKER_URL`;
   - `<SERVICE>_SERVICE_API_KEY`.
2. W profilu `prod` brak którejkolwiek wartości albo pusta wartość kończy start czytelnym `ValueError`/błędem konfiguracji.
3. W profilu `prod` nie wolno używać `SHELL_DATABASE_URL`, `SHELL_EVENTS_BROKER_URL` ani `SHELL_API_KEY` jako fallbacku.
4. Profil `dev` zachowuje obecne wygodne fallbacki i lokalny SQLite.
5. Nie zmieniać jeszcze mechanizmu uwierzytelniania z `X-API-Key`; to osobny etap bezpieczeństwa.

To jest pierwsza zmiana, ponieważ chroni najgroźniejszy błąd separacji: usługę uruchomioną z cudzym lub niejawnym zasobem. Jest mała, nie wymaga migracji schematu ani zmiany kontraktów HTTP/eventowych i można ją wdrożyć przy zachowaniu istniejących obrazów.

## Zakres implementacji

- dodać jawny identyfikator usługi do konfiguracji ładowanej przez każdy entrypoint;
- wprowadzić wspólną funkcję walidującą wymagane sekrety i endpointy produkcyjne;
- zmienić siedem entrypointów, aby najpierw pobierały wartości per usługa, a dopiero w `dev` dopuszczały fallbacki;
- pozostawić monolit i lokalny tryb deweloperski działające bez zmiany zachowania;
- zaktualizować przykłady konfiguracji produkcyjnej oraz dokument wdrożeniowy;
- nie dodawać wyjątków wyciszających istniejące testy architektury.

## Plan wdrożenia

### 1. Zabezpieczyć kontrakt testem

Dodać testy do testów konfiguracji platformy lub testów konkretnej usługi:

- brak bazy w `prod` odrzuca konfigurację;
- brak brokera w `prod` odrzuca konfigurację;
- brak klucza API w `prod` odrzuca konfigurację;
- obecność wyłącznie zmiennych `SHELL_*` nie wystarcza w `prod`;
- komplet zmiennych per usługa pozwala zbudować konfigurację;
- `dev` nadal akceptuje lokalne fallbacki.

### 2. Wprowadzić walidację w jednym miejscu

Zmiana powinna być skupiona w loaderze konfiguracji, z małym adapterem mapującym nazwy środowiskowe usługi. Walidacja musi działać przed utworzeniem kontenera, uruchomieniem migracji i startem serwera.

Komunikaty błędów powinny wskazywać usługę i brakującą nazwę zmiennej, ale nigdy nie wypisywać wartości sekretu ani pełnego URL-a z hasłem.

### 3. Podłączyć siedem composition rootów

Zweryfikować i ujednolicić entrypointy:

- definition;
- execution;
- ingestion;
- project;
- scheduling;
- session;
- user.

Każdy entrypoint ma używać wyłącznie własnych zmiennych w `prod`. Compose już wymaga per-service API key i brokera, więc konfiguracja aplikacji powinna egzekwować ten sam kontrakt także poza Compose.

### 4. Zaktualizować dokumentację i rollout

- poprawić `separacja.md`, usuwając nieaktualny blocker centralnego event registry;
- opisać wymagane zmienne per usługę w dokumentacji wdrożeniowej;
- wdrożyć najpierw na jednej usłudze w stagingu;
- sprawdzić start poprawny, start z brakującą zmienną oraz restart po odtworzeniu sekretu;
- dopiero potem zastosować regułę do pozostałych usług.

## Weryfikacja

Kolejność kontroli:

1. Wąskie testy konfiguracji: `\.venv\\Scripts\\python.exe -m pytest shell/tests/platform/unit/infrastructure/test_shell_config_contract.py -q`.
2. Testy kontraktu wszystkich usług: `\.venv\\Scripts\\python.exe -m pytest shell/tests/architecture/test_independent_service_contract.py shell/tests/architecture/test_standalone_service_surfaces__test_each_bc_has_an_independent_service_surface.py -q`.
3. Testy architektury: `\.venv\\Scripts\\python.exe -m pytest shell/tests/architecture -x`.
4. Test uruchomienia każdego obrazu z kompletem zmiennych per usługę.
5. Test negatywny: usunięcie jednej wymaganej zmiennej ma zakończyć proces przed migracją i otwarciem portu.
6. Test regresyjny `dev`: lokalny SQLite i obecne testy E2E nadal działają.

`deploy.ps1` nie jest zwykłą walidacją, ponieważ wykonuje także commit. Można użyć go wyłącznie jako jawnego końcowego kroku wdrożeniowego po przejściu powyższych kontroli.

## Kryteria akceptacji

- żadna usługa w `prod` nie startuje z pustym kluczem API, pustym brokerem ani domyślnym SQLite;
- usługa nie korzysta z konfiguracji należącej do innego BC;
- błąd konfiguracji jest wykryty przed migracją i przed przyjęciem ruchu;
- tryb `dev` i istniejący monolit pozostają użyteczne;
- wszystkie testy architektury oraz testy negatywne przechodzą;
- dokumentacja opisuje aktualną topologię i rzeczywisty kontrakt uruchomieniowy.

## Rollback

Zmiana jest odwracalna przez wycofanie walidacji w loaderze i przywrócenie poprzednich nazw fallbacków. Nie wymaga cofania migracji ani zmian danych. W produkcji rollback obrazu powinien być wykonany tylko wtedy, gdy poprzednia wersja nadal spełnia ustalony kontrakt sekretów; w przeciwnym razie należy uzupełnić konfigurację, a nie obniżać walidację.

## Następny etap po tej zmianie

Dopiero po ustabilizowaniu konfiguracji produkcyjnej należy zająć się wymianą samego `X-API-Key` na mTLS lub podpisane tokeny, testami awarii zależności oraz pełnym rolloutem rozproszonym. To są ważne zadania, ale mają większy promień zmian i nie powinny wyprzedzać podstawowej gwarancji, że każda usługa startuje z własnymi zasobami i sekretami.
