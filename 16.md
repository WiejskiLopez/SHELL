# Domkniecie Stage 4.4 - usuniecie facade ShellConfig

## 1. Wynik analizy 2.md

Po wykonaniu Stage 4.1, Stage 5 oraz migracji composition roots nie pozostaje
inny punkt o porownywalnym ryzyku architektonicznym. Najwazniejsza pozostala
praca z `2.md` to koncowe domkniecie Stage 4.4:

> usunac monolityczna facade `ShellConfig` po migracji pozostalych callerow na
> jawne fragmenty konfiguracji.

To jest punkt `TODO` w `2.md`, ale jego zakres trzeba ograniczyc. Nie usuwamy
facade, dopoki istnieja callerzy, ktorzy jej potrzebuja.

## 2. Weryfikacja z aktualnym kodem

### Callerzy juz zmigrowani

Siedem service composition roots uzywa slices:

- `deployment_config()` dla `profile` i `database_url`;
- `platform_runtime_config()` dla `events`;
- `service_config()` dla seedowania;
- `auth_config()` w User service.

Potwierdzone pliki:

- `shell/definition_service/bootstrap/definition/main.py`;
- `shell/execution_service/bootstrap/execution/main.py`;
- `shell/ingestion_service/bootstrap/ingestion/main.py`;
- `shell/project_service/bootstrap/project/main.py`;
- `shell/scheduling_service/bootstrap/scheduling/main.py`;
- `shell/session_service/bootstrap/session/main.py`;
- `shell/user_service/bootstrap/user/main.py`.

### Callerzy, ktorych nie wolno usunac bez migracji

Facade jest nadal uzywana bezposrednio przez:

- seed commands: `shell/*_service/bootstrap/*/seed.py`;
- execution CLI: `shell/execution_service/bootstrap/execution/cli/command/*`;
- test helper: `shell/tests/shared/test_db.py`;
- E2E helper: `shell/tests/shared/e2e_helpers.py`;
- publiczny eksport `shell/platform/infrastructure/configuration/__init__.py`.

Wniosek: `ShellConfig` nie jest juz potrzebna service API runtime, ale nadal
jest potrzebna narzedziom pomocniczym i CLI. Usuniecie jej teraz byloby
breaking change bez zamkniecia wszystkich callerow.

## 3. Docelowy podzial ownership

```text
shell/platform/infrastructure/configuration/
    deployment_config.py       # profile, database_url
    platform_runtime_config.py # log_level, events delivery
    auth_config.py             # api_key i auth inputs
    service_config.py          # service-owned optional settings
    config_loader.py            # YAML/env precedence i walidacja
```

Docelowo `ShellConfig` nie jest obiektem runtime. Loader zwraca jawny obiekt
zlozony albo composition root pobiera wymagany fragment bez posiadania
wspolnego worka wszystkich pol.

Zachowac `EventsConfig` jako neutralny model technicznych parametrow delivery.
Registry eventow, routing, queue names i polityki service nie trafiaja do
platformowej konfiguracji.

## 4. Plan realizacji

### Etap 0 - freeze kontraktu

1. Zachowac obecne `ShellConfig.from_environment()` jako facade migracyjna.
2. Dodac test, ktory zapisuje aktualna precedence:
   `defaults -> profile -> component config -> environment`.
3. Dodac testy, ze kazdy slice ma wylacznie pola swojego ownership.
4. Sprawdzic, ze sekret `api_key` nie trafia do logow, exception messages ani
   Problem Details.
5. Nie zmieniac jeszcze eksportow publicznych.

**Dlaczego:** najpierw trzeba zamrozic zachowanie loadera. Bez tego relokacja
moze zmienic precedence i ukryc regresje deploymentu.

### Etap 1 - migracja seed commands

Dla kazdego `shell/*_service/bootstrap/*/seed.py`:

1. pozostawic loader konfiguracji jako wspolny mechanizm;
2. pobrac `deployment_config()` i uzyc `deployment.database_url`;
3. pobrac `service_config()` tylko dla `reset_db` i ustawien seed;
4. usunac bezposredni odczyt `config.database_url`;
5. uruchomic test idempotentnego seedowania danego service.

**Dlaczego:** seed command jest deployment tool, a nie callerem potrzebujacym
calego runtime config. To najmniejsza migracja o niskim ryzyku.

### Etap 2 - migracja CLI commands

Dla execution CLI (`relay_command.py`, `smoke_command.py`) i kazdego kolejnego
service-owned CLI:

1. przyjmowac `DeploymentConfig` lub jawny `database_url` jako input komendy;
2. przyjmowac `PlatformRuntimeConfig`, gdy komenda uruchamia delivery worker;
3. nie przekazywac calego `ShellConfig` w `args.shell_config`;
4. usunac zaleznosc CLI od pol service, ktorych nie uzywa;
5. zachowac format raportow i exit codes.

**Dlaczego:** CLI ma wlasny boundary operacyjny i nie powinno otrzymywac
monolitycznego obiektu konfiguracji tylko dla jednego pola.

### Etap 3 - migracja helperow testowych

1. `shell/tests/shared/test_db.py` powinien otrzymywac `test_db_dir` albo
   dedykowany `TestDatabaseConfig`, zamiast parsowac caly `ShellConfig`.
2. `shell/tests/shared/e2e_helpers.py` powinien otrzymywac jawny test config,
   API key i database URL.
3. Testy platformy konfiguracji nadal testuja loader, ale helpery nie sa juz
   dowodem na potrzebe facade runtime.
4. Usunac import `ShellConfig` z helperow shared.

**Dlaczego:** test helpers nie powinny utrwalac produkcyjnego agregatora jako
publicznego API. Jawne argumenty poprawiaja izolacje i czytelnosc fixture.

### Etap 4 - rozdzielenie loadera od modeli config

1. Przeniesc `_load_yaml`, `_deep_merge`, env precedence i walidacje do
   `config_loader.py`.
2. Loader powinien budowac jawny `LoadedConfig` albo zestaw slices.
3. `ShellConfig` moze pozostac cienkim deprecated adapterem tylko na jeden
   oznaczony cykl migracyjny.
4. Dodac warning/deprecation policy bez logowania sekretow.
5. Ustalic release, w ktorym adapter zostanie usuniety.

**Dlaczego:** mechanizm odczytu konfiguracji nie powinien byc utozsamiany z
jednym monolitycznym modelem wszystkich ustawien.

### Etap 5 - usuniecie facade i enforcement

Po migracji wszystkich callerow:

1. usunac klase `ShellConfig`;
2. zaktualizowac `configuration/__init__.py`;
3. usunac compatibility methods `deployment_config()`,
   `platform_runtime_config()`, `auth_config()` i `service_config()` z facade,
   jesli staly sie niepotrzebne;
4. dodac test architektury zakazujacy nowych importow `ShellConfig` poza
   loader tests albo zatwierdzonym migration module;
5. zaktualizowac `2.md`, `12.md` i ten dokument.

**Dlaczego:** dopiero wtedy ownership jest egzekwowany strukturalnie, a nie
jedynie konwencja callerow.

## 5. Kryteria akceptacji etapow

### Po Etapie 1

- seed commands nie czytaja `config.database_url` bezposrednio;
- seed tests przechodza dla wszystkich service;
- brak zmiany `reset_db` i seed semantics.

### Po Etapie 2

- CLI nie przechowuje calego `ShellConfig` w `args`;
- execution relay/smoke tests przechodza;
- service-owned retention CLI zachowuje ten sam output i exit behavior.

### Po Etapie 3

- shared helpers uzywaja jawnych test config inputs;
- platform config tests nadal pokrywaja loader i precedence;
- zadna fixture nie wymaga produkcyjnego facade.

### Po Etapie 5

- brak nieuzasadnionych importow `ShellConfig`;
- composition roots, CLI, seed i test helpers maja jawne ownership;
- pelny test platform, service, contracts i architecture przechodzi;
- ruff, mypy i import-linter przechodza;
- brak zmiany kontraktow HTTP/event/delivery.
