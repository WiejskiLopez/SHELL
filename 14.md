# Stage 4.4 - przepiecie composition roots na config slices

## 1. Weryfikacja krytycznego punktu z 2.md

W `2.md` pozostaje krytyczny punkt:

> `ShellConfig` ma fail-fast loader i typed slices, ale composition roots nadal
> korzystaja z monolitycznego obiektu konfiguracji.

Weryfikacja kodu potwierdza to w siedmiu bootstrapach:

- `shell/definition_service/bootstrap/definition/main.py` czyta `database_url`,
  `events` i `seed_dev_data`;
- `shell/execution_service/bootstrap/execution/main.py` czyta `database_url`,
  `events` i `seed_dev_data`;
- `shell/ingestion_service/bootstrap/ingestion/main.py` czyta te same pola;
- `shell/project_service/bootstrap/project/main.py` czyta te same pola;
- `shell/scheduling_service/bootstrap/scheduling/main.py` czyta te same pola;
- `shell/session_service/bootstrap/session/main.py` czyta te same pola;
- `shell/user_service/bootstrap/user/main.py` dodatkowo czyta `api_key`.

`config_slices.py` juz posiada `DeploymentConfig`, `PlatformRuntimeConfig`,
`AuthConfig` i `ServiceConfig`, wiec brakujaca praca jest migracja callerow,
a nie nowa abstrakcja.

## 2. Decyzja

Wykonujemy teraz migracje composition roots na slices, zachowujac
`ShellConfig` jako facade loadera. Nie usuwamy facade, poniewaz nadal jest
uzywana przez CLI, seed commands, test helpers i inne sciezki pomocnicze.

Ownership:

- `DeploymentConfig`: `profile`, `database_url`;
- `PlatformRuntimeConfig`: `log_level`, techniczne `events` delivery;
- `AuthConfig`: `api_key`;
- `ServiceConfig`: `max_step`, `max_parallel`, `seed_dev_data`, `reset_db`.

## 3. Zakres zmian

### Etap 1 - bootstrap API services

W kazdym `bootstrap/*/main.py`:

1. utworzyc lokalne slices po `ShellConfig.from_environment()`;
2. uzywac `deployment.database_url` dla bazy service;
3. uzywac `runtime.events` dla brokera, heartbeat i polling;
4. uzywac `service.seed_dev_data` dla seedowania;
5. w User przekazywac `auth.api_key` do factory;
6. nie zmieniac argumentow CLI ani uruchamiania uvicorn/workera.

### Etap 2 - worker helpers

Przepiac pomocnicze `_run_event_worker`, relay commands i worker startup na
`PlatformRuntimeConfig`, ale tylko tam, gdzie caller ma jawny config slice.
Nie przenosic jeszcze konfiguracji do globalnego singletona.

### Etap 3 - enforcement

Dodac test architektury, ktory:

- wymaga uzycia `deployment_config()`, `platform_runtime_config()`,
  `service_config()` lub `auth_config()` w composition roots;
- zabrania nowych bezposrednich odczytow `config.database_url`, `config.events`,
  `config.seed_dev_data` i `config.api_key` w bootstrapach;
- pozwala facade w test helpers i CLI do czasu kolejnej migracji;
- potwierdza, ze `database_url` jest wartoscia deploymentu service, nie
  ustawieniem platformowego runtime.

## 4. Kolejnosc i walidacja

1. Przepiac Definition i Execution, uruchomic ich standalone tests.
2. Przepiac pozostale service API bootstrapy, uruchomic service E2E.
3. Przepiac User auth, uruchomic auth middleware i User E2E.
4. Dodac enforcement dopiero po migracji wszystkich siedmiu main.py.
5. Na koncu uruchomic platform, architecture, contracts, ruff, mypy i
   import-linter.

## 5. Kryteria akceptacji

- wszystkie siedem service bootstrap main korzysta z config slices;
- runtime zachowuje dotychczasowe porty, worker flags, seed behavior i auth;
- facade `ShellConfig` nie istnieje; niemigrowane sciezki uzywaja
  `LoadedConfiguration` albo jawnych test inputs;
- brak bezposrednich odczytow monolitycznego config w service main;
- testy architektury potwierdzaja ownership konfiguracji;
- brak zmiany kontraktow HTTP/event/delivery.

## 6. Rollback

1. Cofac migracje pojedynczego bootstrapu do odczytow facade.
2. Nie usuwac `config_slices.py` ani walidacji Fazy 1.
3. Nie przywracac profilu `dev` jako defaultu.
4. Po rollbacku uruchomic testy danego service i konfiguracji.
