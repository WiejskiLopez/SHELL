# Plan etapowy wdrożenia reorganizacji `shell/platform/`

> Na podstawie `1.md` (struktura docelowa) i analizy wniosków.
>
> **Nadrzędna zasada:** serwisy (BC) muszą cały czas działać. Żaden etap nie może
> złamać importów ani zachowania platformy między etapami. Każdy etap kończy się
> weryfikacją przez `.\run_tests.ps1` (wyrocznia wg `run-tests-validator`).

## Wzorzec bezpiecznej relokacji pliku (używany we wszystkich etapach przenoszenia)

Dla każdego przenoszonego modułu `X`:

1. `git mv` starej ścieżki na nową (np. `domain/value_objects/created_at.py` → `domain/value_objects/time/created_at.py`).
2. W **starym miejscu** zostaje cienki shim re-exportujący (deprecated):
   ```python
   # DEPRECATED: użyj shell.platform.<nowa_ścieżka>
   from shell.platform.<nowa_ścieżka> import CreatedAt  # noqa: F401
   ```
   Dzięki temu **żaden importer (BC) nie musi się zmieniać w tym etapie** — wszystko działa.
3. W pomniejszym, dedykowanym podkroku `migracja importów` aktualizujemy referencje w BC do nowych ścieżek.
4. W **ostatnim etapie** (STAGE 11) usuwamy wszystkie shimy.

Gdzie zestaw plików jest mały i dobrze zamknięty — relokacja + migracja importów + usunięcie shima mieszczą się w tym samym etapie (oznaczone: „pełny move”).

## Weryfikacja (definicja gotowości etapu)

Każdy etap kończy się dopiero, gdy:
1. **Szybka kontrola** (podczas pracy): `python -m ruff check shell shell/tests` + `python -m mypy --no-incremental shell` + `import-linter lint`.
2. **Pełna wyrocznia:** `.\run_tests.ps1` `-UnitOnly` przy małych zmianach, a pełne `.\run_tests.ps1` dla etapów dotykających delivery, API i integracji.
3. Jeśli skrypt padnie → pokazuję userowi błąd i pytam o decyzję (nie naprawiam na ślepo).
