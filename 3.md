# Krok 1: pierwszy weryfikowalny mikroserwis

## Decyzja

Pierwszym realnym krokiem będzie doprowadzenie `user_service` do stanu, w którym można go **zbudować, uruchomić, przetestować i wdrożyć bez kodu biznesowego pozostałych sześciu usług**.

Nie wykonujemy jeszcze tej samej operacji równolegle dla wszystkich BC. `user_service` jest pilotem i wzorcem. Dopiero po spełnieniu kryteriów akceptacji powielimy rozwiązanie dla `definition_service`, `execution_service`, `ingestion_service`, `project_service`, `scheduling_service` i `session_service`.

## Dlaczego to jest najważniejszy pierwszy krok

Obecny [Dockerfile user_service](shell/user_service/docker/Dockerfile) kopiuje `pyproject.toml` oraz całe `shell/`, a następnie instaluje wspólny projekt `shell`. W efekcie proces jest osobny, ale granica artefaktu nie jest jeszcze niezależna.

Dopóki nie udowodnimy, że jeden mikroserwis może powstać z własnego kodu oraz wersjonowanej platformy, nie mamy wiarygodnej podstawy do dalszych zmian w bazach, kontraktach i operacjach. Ten krok daje prosty test rzeczywistej niezależności, a nie tylko test poprawnej struktury katalogów.

## Stan obecny i stan docelowy

### Obecnie

```text
root pyproject.toml
    -> jeden projekt shell
    -> cały katalog shell/
    -> kod platformy + kod wszystkich usług
    -> Dockerfile user_service kopiuje cały shell/
```

### Po wykonaniu kroku

```text
shell-platform==X.Y.Z
    -> tylko generyczne shell.platform

shell-user-service==A.B.C
    -> tylko shell.user_service
    -> zależy od konkretnej wersji shell-platform
    -> komunikuje się z innymi usługami przez HTTP/eventy
```

Docelowa zależność ma wyglądać tak:

```text
user_service -> shell-platform
user_service --HTTP/event contract--> inne mikroserwisy
shell-platform -X-> jakikolwiek konkretny mikroserwis
```

Strzałka oznaczona `-X->` oznacza zakaz zależności platformy od bounded contextu.

## Zakres zmian: co zmienić i na co

### 1. Artefakt platformy

- Utworzyć osobną definicję pakietu `shell-platform` obejmującą wyłącznie `shell.platform`.
- Zostawić w platformie tylko elementy generyczne: Unit of Work lifecycle, inbox/outbox, serializację koperty, transport, HTTP client, logging, identity, time, health/readiness i retry.
- Usunąć z artefaktu platformy każdy import lub registry zawierające `shell.*_service`.
- Nadać platformie wersję semantyczną, np. `shell-platform 0.1.0`.
- Opublikować wheel platformy do lokalnego repozytorium artefaktów używanego przez build pilota.

### 2. Artefakt `user_service`

- Utworzyć osobną definicję pakietu `shell-user-service` obejmującą wyłącznie kod `shell.user_service`.
- Do zależności `shell-user-service` wpisać konkretną wersję `shell-platform`, a nie kod platformy przez import z tego samego projektu.
- Do zależności dodać tylko biblioteki potrzebne przez User BC.
- Nie dodawać żadnej zależności na `definition_service`, `execution_service`, `ingestion_service`, `project_service`, `scheduling_service` ani `session_service`.
- Własne eventy User BC zostawić w `user_service`; publiczne eventy zewnętrzne opisywać jako wersjonowane kontrakty, a nie importować klasy obcej usługi.

### 3. Dockerfile pilota

Zmienić [Dockerfile user_service](shell/user_service/docker/Dockerfile):

- z:
  - `COPY pyproject.toml ./`;
  - `COPY shell/ ./shell/`;
  - `pip install -e .`;
  - uruchamianie kodu z całego wspólnego pakietu;
- na:
  - instalację konkretnego wheel `shell-platform`;
  - instalację konkretnego wheel `shell-user-service`;
  - kopiowanie tylko plików wymaganych przez User BC i jego konfigurację runtime;
  - uruchamianie `shell.user_service.bootstrap.user.main`;
  - przekazywanie `DATABASE_URL`, adresu brokera i klucza API przez środowisko/sekrety, bez wartości produkcyjnych w obrazie.

Obraz pilota nie może zawierać katalogów ani modułów biznesowych pozostałych usług.

### 4. Konfiguracja User BC

- Wydzielić konfigurację User BC z konfiguracji globalnej do własnego namespace, np. `USER_SERVICE_*`.
- Pozostawić w platformie wyłącznie parser i walidator generycznych ustawień, bez wiedzy o wszystkich usługach.
- `user_service` ma otrzymywać własny adres bazy, własny użytkownik bazy, własne sekrety oraz własny adres brokera.
- Domyślne dane typu `shell:shell` i `dev-user-key` mogą istnieć wyłącznie w jawnie oznaczonym środowisku lokalnym/testowym, nigdy w obrazie produkcyjnym.

### 5. Kontrakty z innymi usługami

- Sprawdzić każdy import spoza `shell.user_service` i `shell.platform`.
- Zamienić bezpośredni import obcej implementacji na lokalny port oraz adapter HTTP albo konsumenta eventu.
- Umieścić kontrakt, którego User BC potrzebuje, w katalogu kontraktów publicznych lub zdefiniować jego lokalną reprezentację zgodną ze schematem wire.
- Dla eventów używać stabilnego `event_type`, `schema_version`, `event_id`, `correlation_id` i `causation_id`.
- Nie współdzielić modeli ORM, repozytoriów, query service ani klas domenowych między usługami.

### 6. Budowanie i pipeline

- Dodać osobny krok budowania `shell-platform` oraz osobny krok budowania `shell-user-service`.
- Dodać osobny lockfile lub równoważny, powtarzalny zapis zależności dla User BC.
- Publikować obraz jako `user-service:<version>` oraz `user-service:<git-sha>`.
- Pipeline User BC ma uruchamiać testy User BC, testy kontraktów, test izolacji importów i budowę obrazu.
- Zmiana pliku należącego wyłącznie do innego mikroserwisu nie może wymuszać nowego release’u `user_service`.
- Aktualizacja `shell-platform` ma być jawnie widoczna jako zmiana wersji zależności User BC.

## Test weryfikujący krok

Do repozytorium dodać test/polecenie weryfikacyjne, które wykonuje poniższe czynności na czystym katalogu tymczasowym:

1. Buduje wheel `shell-platform`.
2. Buduje wheel `shell-user-service` z jego własnej definicji pakietu.
3. Buduje obraz User BC bez kopiowania całego katalogu `shell/`.
4. Sprawdza, że obraz zawiera `shell.platform` i `shell.user_service`, ale nie zawiera `shell.definition_service`, `shell.execution_service`, `shell.ingestion_service`, `shell.project_service`, `shell.scheduling_service` ani `shell.session_service`.
5. Uruchamia User BC z własną testową bazą i minimalną konfiguracją.
6. Sprawdza odpowiedź `/health` oraz `/readiness`.
7. Wykonuje reprezentatywne żądanie User API bez uruchamiania pozostałych usług.
8. Sprawdza statycznie, że kod User BC nie importuje innego `*_service`.
9. Uruchamia testy User BC i istniejące testy architektury.
10. Modyfikuje plik innego mikroserwisu i potwierdza, że artefakt oraz digest obrazu User BC nie zmieniają się.

Przykładowy kontrakt testu izolacji:

```text
build user-service == success
run user-service without other BC source == success
GET /health == 200
GET /readiness == 200 when own dependencies are ready
import user_service -> only user_service + platform + external packages
image contains no other BC implementation
unrelated BC change -> user-service artifact unchanged
```

## Kryteria akceptacji

Krok jest ukończony dopiero wtedy, gdy wszystkie warunki są spełnione:

- `shell-platform` ma własną wersję i można zbudować jego wheel niezależnie;
- `shell-user-service` ma własną wersję, lockfile i można zbudować jego wheel niezależnie;
- Dockerfile User BC nie kopiuje całego `shell/`;
- obraz User BC nie zawiera implementacji pozostałych bounded contextów;
- User BC uruchamia się z własną bazą i własną konfiguracją bez pozostałych procesów;
- User BC nie importuje żadnego innego `*_service`;
- platforma nie importuje żadnego `*_service`;
- komunikacja z innymi usługami przechodzi tylko przez publiczny HTTP/event contract;
- migracja User BC nie ładuje modeli pozostałych usług;
- healthcheck i readiness działają osobno;
- testy pilota, testy kontraktowe i `pytest shell/tests/architecture -x` przechodzą;
- zmiana kodu innego mikroserwisu nie zmienia artefaktu User BC;
- aktualizacja platformy wymaga jawnej, kontrolowanej zmiany wersji zależności.

## Czego nie robić w tym kroku

- Nie przenosić jeszcze wszystkich siedmiu usług naraz.
- Nie kopiować platformy do `user_service`.
- Nie przenosić logiki biznesowej User BC do platformy.
- Nie tworzyć wspólnego „contract package”, który zawiera implementacje domenowe wszystkich usług.
- Nie utrzymywać trybu, w którym produkcyjny User BC automatycznie ładuje monolityczny kontener wszystkich BC.
- Nie uznawać przejścia testów importów za dowód pełnej niezależności; wymagany jest także build, start i test obrazu w izolacji.

## Wynik po kroku

Po wykonaniu tego kroku będziemy mieć pierwszy dowód, że granica mikroserwisu działa w praktyce:

```text
User BC = własny kod + shell-platform + własne dane + własny kontrakt + własny release
```

Jeżeli którykolwiek test akceptacyjny nie przejdzie, nie rozpoczynamy wydzielania następnego BC. Najpierw poprawiamy granicę pilota, ponieważ każdy pozostały mikroserwis powinien później użyć tego samego, sprawdzonego wzorca.

## Definicja sukcesu w jednym zdaniu

> **Można usunąć z kontekstu budowania cały kod sześciu pozostałych usług, zbudować i uruchomić `user_service`, obsłużyć jego API oraz wydać nową wersję bez ich budowania i wdrażania.**
