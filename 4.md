# Etap 2: niezależny i powtarzalny release mikroserwisu

## Decyzja

Kolejnym weryfikowalnym etapem będzie formalne potwierdzenie, że `user_service` można wydać jako niezależny artefakt z czystego commita oraz wskazać go niezmiennym digestem obrazu.

Ten etap nie polega na dalszym wydzielaniu katalogów. Pakiet, lockfile, Dockerfile, migracje, konfiguracja i testy pilota już istnieją. Teraz trzeba udowodnić, że wydanie jest powtarzalne i nie zależy od przypadkowego stanu pozostałej części monorepo.

Publikacja do GHCR nie jest częścią tego etapu. Testy mogą korzystać z lokalnych obrazów Docker. Push do rejestru pozostaje osobną decyzją operacyjną.

## Status realizacji

### Weryfikacja lokalna: ZAKOŃCZONA

Lokalny verifier etapu został wykonany pomyślnie bez publikacji do GHCR. Sprawdził lockfile, budowę wheels, obraz, RabbitMQ, osobnego workera, readiness `503 -> 200`, reprezentatywne API oraz niezmienność kontrolowanego digestu filesystemu po zmianie nieużywanego BC.

- [x] powtarzalne zbudowanie wheels;
- [x] zbudowanie obrazu User BC;
- [x] uruchomienie API, RabbitMQ i osobnego workera;
- [x] readiness `503` bez workera;
- [x] readiness `200` po świeżym heartbeat workera;
- [x] reprezentatywne żądanie User API;
- [x] manifest release z wersją, commitem, image ID i sumami wheels;
- [x] test wpływu zmiany `definition_service` na obraz User BC;
- [x] kontrola clean working tree w trybie release.

Ostatni punkt został zaimplementowany i zweryfikowany negatywnie na bieżącym workspace: repozytorium ma niezatwierdzone zmiany, więc formalny release bez `--allow-dirty` jest prawidłowo odrzucany. Po utworzeniu czystego commita można wykonać ten sam verifier bez `--allow-dirty`.

- [x] każda usługa ma własny parametr, port, worker, bazę i trasę OpenAPI;

- [x] każda usługa przechodzi `/readiness = 200` po świeżym heartbeat workera;
- [x] każda usługa działa z lokalnym RabbitMQ i osobnym procesem workera;
- [x] każda usługa ma sprawdzony niezależny artefakt i obraz;
- [x] matrix workflow obejmuje wszystkie pozostałe usługi;
- [x] test manifestu release działa dla wszystkich siedmiu pakietów w trybie dry-run;
- [x] lokalnie wykonano pełny test kontenerowy wszystkich siedmiu obrazów.

Formalny release manifest z digestem każdego obrazu nadal wymaga wykonania na czystym commicie per usługa. W tej sesji wykonano lokalną weryfikację runtime wszystkich usług oraz test manifestów w trybie dry-run z `--allow-dirty`; nie jest to jeszcze produkcyjny release zatwierdzonego źródła.

## Dlaczego to jest następny ważny krok

Obraz może być zbudowany i uruchomiony, ale bez tego etapu nadal nie mamy pełnego dowodu, że:

- obraz pochodzi z zatwierdzonego źródła;
- ten sam kod daje ten sam artefakt;
- zmiana innego mikroserwisu nie zmienia obrazu User BC;
- wdrożenie może wskazywać konkretny, niezmienny digest zamiast ruchomego taga;
- pipeline nie publikuje przypadkowego obrazu z niezatwierdzonych zmian.

To jest granica między lokalnym dowodem technicznym a kontrolowanym procesem release.

## Stan obecny i stan docelowy

### Obecnie

```text
working tree
    -> może zawierać niezatwierdzone zmiany
    -> lokalny build obrazu
    -> tag 0.1.0 lub local-...
    -> ręczna weryfikacja obrazu
```

### Po wykonaniu etapu

```text
clean commit
    -> locked dependencies
    -> deterministic build
    -> shell-user-service:<version>
    -> image digest sha256:...
    -> release manifest
    -> optional local registry / GHCR publication
```

Wdrożenie ma wskazywać digest:

```text
ghcr.io/wiejskilopez/shell/shell-user-service@sha256:<digest>
```

Tag wersji służy do wyszukiwania obrazu, a digest gwarantuje, że późniejsze przesunięcie taga nie zmieni wskazanego artefaktu.

## Zakres zmian: co zmienić i na co

### 1. Czysty punkt źródłowy

- Dodać kontrolę w pipeline, która przed buildem sprawdza, czy working tree nie zawiera niezatwierdzonych zmian.
- Budować obraz wyłącznie z konkretnego commita lub taga release.
- Odróżnić build developerski od release builda.
- Nie używać tagu `local-*` jako tagu produkcyjnego.
- Do release używać taga semver, np. `v0.1.0`, oraz SHA commita.

Przykładowe warunki:

```text
git status --porcelain == empty
release tag == v<major>.<minor>.<patch>
source commit == commit recorded by CI
```

### 2. Powtarzalne zależności

- Pipeline ma używać właściwego lockfile konkretnego mikroserwisu.
- Build ma kończyć się błędem, jeżeli lockfile nie odpowiada manifestowi pakietu.
- Wersja `shell-platform` ma być jawnie zapisana w zależnościach User BC.
- Nie instalować zależności przez niekontrolowane `pip install -e .` z root repozytorium.
- Publikować lub archiwizować sumy kontrolne wheels razem z raportem release.

### 3. Deterministyczny obraz

- Ustawić stały `SOURCE_DATE_EPOCH` dla budowania wheels.
- Używać przypiętej wersji obrazu bazowego Python albo kontrolować jego digest.
- Wyłączyć niekontrolowane provenance, cache i timestampy w wariancie testu reprodukowalności.
- Zbudować obraz co najmniej dwa razy z tego samego commita.
- Porównać digest albo, gdy narzędzie budowania dodaje zmienne metadane, porównać digest zawartości filesystemu obrazu i jawnie zapisać różnicę.
- Nie dodawać do obrazu logów, baz developerskich, sekretów ani kodu testowego.

### 4. Test wpływu zmiany innego BC

- Przygotować tymczasowy kontekst builda zawierający `shell.platform` i `shell.user_service`.
- Zbudować obraz User BC i zapisać jego identyfikator oraz digest.
- Dodać lub zmienić plik w `definition_service`.
- Zbudować obraz User BC ponownie z tym samym stanem User BC i platformy.
- Potwierdzić, że digest zawartości obrazu User BC się nie zmienił.
- Wykonać ten sam test dla co najmniej jednego innego mikroserwisu jako potwierdzenie uniwersalności wzorca.

Ważne: test nie powinien porównywać tylko tagów. Tag może wskazywać inny obraz. Porównywany musi być digest lub kontrolowana suma zawartości obrazu.

### 5. Manifest release

Dla każdego release zapisać:

- nazwę mikroserwisu;
- wersję pakietu;
- SHA commita;
- digest obrazu;
- wersję `shell-platform`;
- wersję lockfile;
- datę i wynik testów;
- status migracji bazy;
- listę publicznych wersji kontraktów.

Manifest może być plikiem JSON generowanym przez pipeline, np.:

```json
{
  "service": "shell-user-service",
  "version": "0.1.0",
  "commit": "<full-git-sha>",
  "image": "ghcr.io/wiejskilopez/shell/shell-user-service",
  "image_digest": "sha256:<digest>",
  "platform_version": "0.1.0",
  "migration_head": "0001_user_baseline",
  "status": "verified"
}
```

Manifest nie zawiera sekretów.

### 6. Pipeline release

Rozszerzyć workflow User BC o osobne kroki:

1. sprawdzenie clean working tree w checkout CI;
2. sprawdzenie lockfile;
3. testy User BC, kontraktów i architektury;
4. budowę wheels z `SOURCE_DATE_EPOCH`;
5. budowę obrazu bez kodu innych BC;
6. uruchomienie obrazu z testowym brokerem i workerem;
7. sprawdzenie `/health`;
8. sprawdzenie `/readiness = 503` bez workera;
9. sprawdzenie `/readiness = 200` po heartbeat workera;
10. sprawdzenie reprezentatywnego API;
11. pobranie digestu obrazu;
12. wygenerowanie manifestu release;
13. opcjonalne zapisanie obrazu w lokalnym registry lub publikację do GHCR tylko po jawnej decyzji release.

Workflow dla pull requesta nie powinien publikować obrazu do GHCR. Publikacja może być dozwolona wyłącznie dla taga release.

## Test weryfikujący etap

Dodać test lub skrypt `verify_service_release.py`, który wykonuje:

```text
1. odrzuca dirty source tree;
2. sprawdza lockfile;
3. buduje platform wheel;
4. buduje User wheel;
5. buduje obraz User BC;
6. sprawdza brak kodu pozostałych BC;
7. uruchamia RabbitMQ, API i workera;
8. sprawdza readiness 503 bez workera;
9. sprawdza readiness 200 po heartbeat workera;
10. wykonuje reprezentatywne żądanie API;
11. zapisuje digest obrazu;
12. zmienia plik innego BC;
13. buduje User BC ponownie;
14. porównuje digest zawartości obrazu;
15. tworzy release manifest.
```

Test powinien zwracać błąd, gdy:

- źródło jest nieczyste;
- lockfile jest nieaktualny;
- obraz zawiera inny BC;
- worker nie zapisuje heartbeat;
- readiness nie zmienia się z `503` na `200`;
- API nie działa;
- digest zmienia się po zmianie nieużywanego BC;
- manifest nie zawiera SHA, wersji lub digestu.

## Kryteria akceptacji

Etap jest zakończony dopiero wtedy, gdy:

- release buduje się z czystego commita;
- obraz User BC można zbudować bez kodu pozostałych usług;
- wheels i lockfile są powtarzalne;
- obraz ma tag wersji oraz tag/odniesienie do commita;
- digest obrazu jest zapisany w release manifest;
- `/health` zwraca `200`;
- `/readiness` zwraca `503` bez aktywnego workera;
- `/readiness` zwraca `200` po aktywacji workera i świeżym heartbeat;
- reprezentatywne API User BC działa;
- zmiana pliku innego BC nie zmienia digestu zawartości User BC;
- testy User BC, kontraktów i architektury przechodzą;
- pipeline PR nie publikuje do GHCR;
- publikacja release jest osobnym, jawnym krokiem;
- nie ma sekretów w obrazie, wheelach ani manifeście.

## Czego nie robić w tym etapie

- Nie wdrażać jeszcze produkcji.
- Nie publikować automatycznie każdego obrazu do GHCR.
- Nie używać `latest` jako identyfikatora wdrożenia.
- Nie traktować taga jako zamiennika digestu.
- Nie porównywać wyłącznie rozmiaru obrazu.
- Nie uznawać tego etapu za zakończony tylko dlatego, że `docker build` kończy się sukcesem.
- Nie zmieniać jednocześnie domeny wszystkich mikroserwisów.
- Nie dodawać do `platform` logiki dotyczącej release’u jednego BC.

## Wynik po etapie

Po wykonaniu otrzymamy pierwszy kontrolowany release:

```text
User BC = clean commit + locked dependencies + own wheels + own image + digest + release manifest
```

Będziemy mogli jednoznacznie odpowiedzieć:

> „Ten konkretny obraz User BC pochodzi z tego commita, zawiera tylko User BC i platformę, przechodzi testy gotowości, a zmiana innej usługi nie wpływa na jego artefakt.”

## Definicja sukcesu w jednym zdaniu

> **Z czystego commita można powtarzalnie zbudować User BC, uruchomić go z workerem, potwierdzić readiness `503 -> 200`, zapisać jego digest i wykazać, że zmiana innego mikroserwisu nie zmienia jego obrazu.**
